# 自主技巧判定與編譯契約

> 本文件決定「產物內需要哪些技巧」，不是選擇模型、供應商或執行工具的智慧路由。只有能合理改善當前任務的技巧才納入成品。

## 目標驅動的查證與編譯流程

此流程是可觀察的工作契約，不要求模型揭露私有思維鏈。依風險調整流程深度；單步簡單任務可以合併步驟，但不可省略必要的目標保真與交付檢查。

1. **理解問題**：辨識真實意圖、預期成品（Prompt／Skill／Agent）、使用環境、固定限制、授權與不可變更的決策。不把推定當作明示要求。
2. **定義目標與成功標準**：用可觀察輸出描述「完成」；同步記下使用者將如何驗收。無法客觀判定的風格品質，保留人工 QC 權限。
3. **資訊缺口盤點**：分出已確認事實、待查證資料、合理假設與真正阻塞的未知事項。只查影響結果的資訊。
4. **按需查證與證據閘門（Evidence Gate）**：當任務依賴最新資訊、專業事實、平台版本、工具能力或來源內容時才檢索。證據充分則推進；部分充分則標示假設與限制；關鍵證據不足則查證或標記阻塞，不捏造。設計途中發現新缺口可回到此步。
5. **設計流程及判定技巧**：根據依賴順序、失敗模式、可用工具與預期效益，選擇最少必要技巧；不以智慧模型路由或固定清單代替判斷。外部副作用需要權限、冪等及停止契約。
6. **編譯雙份產物**：一份乾淨可用的正式成品，另一份獨立繁體中文使用說明；不讓第二份成為成品的隱性依賴。
7. **實際輸出檢驗**：以至少一個正常案例、必要時再用邊界與失敗案例試用產物，檢查輸出品質、限制保真、可複製性、可安裝性及依賴完整度。具備真實模型、工具與 Runtime 才宣稱行為驗收；否則只報告靜態檢查與人工示例。
8. **有界自我迭代**：若驗收失敗，記錄「輸入／實際輸出／預期差異／根因／修正／重測」。只修有證據的問題，不自行更改成功條件；最多 3 輪，兩輪沒有實質改善即停止。通過前不得標示「已驗收」；停下而未通過應標記未完成與缺口。
9. **使用者 QC 閉環**：內部驗收通過才交付。使用者部署／貼用後的實測回饋，作為下一輪獨立驗收資料；重現、修復、回歸測試、升版交付，不把初次交付當永久結案。不得假設使用者已完成 QC。

可在內部使用決策紀錄 `{technique, target_failure, expected_gain, prerequisites, overhead, chosen, evidence}`，及驗證紀錄 `{case, expected, observed, evidence_level, status, fix, retest}`；對使用者只交付必要摘要、成果與驗證證據，不揭露私有思維鏈。

### 驗收證據等級

- **L0 規格**：有書面指令或待測案例；未執行。
- **L1 靜態驗證**：結構、連結、依賴與測試程式通過；不代表產生的文字符合需求。
- **L2 範例試產與人工審查**：確實產出樣本，依案例逐項核對；不等同正式模型端到端成功。
- **L3 真實運行驗收**：在目標模型和工具環境執行，保存輸入、輸出、工具結果與驗收證據。
- **L4 使用者 QC**：使用者實際使用後給出具體回饋，並完成必要修正與再驗證。

不得用 L1 冒稱 L3 或 L4；缺少平台權限或實際執行器時，清楚標註可交付程度。

## 技巧候選與適用條件

| 技巧 | 需要時採用 | 不需要時避免 |
| --- | --- | --- |
| Zero-shot / 直接任務指令 | 任務清楚、格式簡單 | 不因形式要求附長範例 |
| Few-shot（少樣本） | 邊界或風格難以文字界定，且有代表性正確範例 | 無可靠範例、容易過度模仿 |
| Structured Output（結構化輸出） | 下游程式解析、欄位契約嚴格 | 一般自然語言不必強制 JSON |
| Task Decomposition（任務分解） | 工作有依賴、分階段驗證的必要 | 一步任務不拆成冗長流程 |
| Retrieval Grounding（檢索依據） | 答案依賴外部或近期事實 | 不虛構來源或檢索權限 |
| Context Engineering（上下文工程） | 長文件、多來源、歷史狀態需節制載入 | 不無差別塞入所有歷史 |
| ReAct / Tool Calling（行動與工具調用） | 已確認工具可執行且結果影響後續步驟 | 僅寫提示詞或無工具時不假裝有工具 |
| Plan-and-Execute（規劃後執行） | 多步驟外部操作、依賴明確 | 不強迫簡單任務先規劃 |
| Reflection / Evaluator–Optimizer（驗證修正） | 有可辨認缺陷和外部驗收器 | 無證據自我打分、無界反思 |
| Checkpoint / Resume（檢查點續跑） | 長時間任務、中斷後恢復很重要 | 無持久儲存能力時不得宣稱已實作 |
| Idempotency（冪等保護） | 發布、付款、建立資源等可能重複副作用 | 非冪等操作超時不得盲目重送 |
| Multi-Agent（多代理協作） | 可明確拆分獨立工作且效益大於協調成本 | 單一代理已足夠時不硬加 |
| Agent Memory（代理記憶） | 跨回合任務須追蹤已確認狀態 | 不把即時猜測寫入長期記憶 |
| Human Approval（人工批准） | 外部寫入、高影響操作或權限限制要求 | 已有精確有效授權時不重複追問 |
| Model Adapter（模型適配） | 目標平台有已確認的不同模型規格 | 不因模型品牌推定工具功能 |

這不是封閉技巧表。可採納新技巧，但必須同樣說明失敗模式、效果、先決條件與驗證方式；不得把新穎程度當作採納理由。

## 按產物型別編譯

- **Prompt**：直接把必要的輸入、輸出、例子、證據或格式限制寫入完整可複製的提示詞，不加入執行端不存在的狀態管理。
- **Skill**：以 `SKILL.md` 定義觸發邊界與最小執行契約；較長的專業技術放參考檔，明確說明何時載入。避免所有技巧永久進入上下文。
- **Agent**：需有能力、工具、狀態、權限、成本、失敗復原及停止條件的實際契約；不需要某項能力就不加入。區分模型規則與宿主 Runtime 才能強制的限制。

## 交付前必查

- 每一個編入的技巧是否能對應具體需求或失敗模式？
- 是否有更簡單方式得到同等結果？
- 是否保留所有使用者明示限制、已鎖定決策與目標環境邊界？
- 是否誠實區分靜態規格、模擬結果與真正執行證據？
- 是否有「不使用某技巧」的理由，尤其是多代理、無界循環與持久記憶？

## 固定雙份交付契約

每次編譯均產出兩份邏輯上分離的交付物：

1. **乾淨正式版**：直接可用的完整 Prompt、Skill 或 Agent。不得混入研究筆記、解釋性前言、驗收過程或無效占位符；保留執行所必需的規則、變數定義與依賴。若缺少必要平台工具，明確標示尚未就緒，不得宣稱即裝即用。
2. **繁體中文使用說明**：用途、適用範圍、前置條件、安裝或貼上位置、啟用方式、必要輸入、操作範例、驗證方法、限制及故障排除。不得讓說明文件成為正式版執行的隱藏必要依賴。

Skill 預設交付 `skill-package.zip` 與 `使用說明.md`；Prompt 預設交付可直接複製的正式提示詞與獨立使用說明；Agent 預設交付完整可部署設定（視目標平台提供必要檔案）與獨立操作說明。無檔案工具時提供兩個清楚分隔、可複製的完整內容，不得謊稱已產出壓縮檔。

### GitHub PR 自動完成原則

在使用者已授權的改版範圍內，預設完成修改、測試、修復、驗收後直接合併 PR，不把人工點擊 Merge 當作常規步驟。合併前確認分支、最新提交、必要檢查、合併衝突及儲存庫保護要求；若有未通過檢查、重大風險或權限不足則停止並回報，不得繞過保護規則。此規則只對具有實際 GitHub 寫入工具與使用者授權的執行環境有效。
