# Agent 執行契約

> 只有在提示詞會讓模型自主規劃、反覆使用工具、維護狀態或處理長任務時讀取。

導覽：[選擇架構](#先選-workflow-或-agent) · [迴圈契約](#有界迴圈契約) · [狀態](#狀態與長任務) · [失敗](#失敗分類) · [完成](#完成與驗證) · [骨架](#可複製骨架)

## 先選 Workflow 或 Agent

- 任務步驟穩定、分支可枚舉、失敗成本高：優先建立 Workflow（工作流程），由程式控制路徑。
- 任務步驟無法預先枚舉、需要依觀察調整：才建立 Agent（代理）。
- 只需要一次模型回覆或單次工具呼叫時，不建立自主迴圈。
- 混合架構可用固定 Workflow 包住少數需要判斷的 Agent 節點。

## 有界迴圈契約

Loop Engineering（迴圈工程）沿用本文件的執行迴圈，不再建立第二套重複的代理流程。

- **啟用條件：** 任務需要依結果反覆調整，有可使用的驗收器，且能設定授權邊界與有限預算。一次回答或主觀創意討論不預設啟用。
- **驗收對象：** 先分清提示詞文字、模型產出，或外部操作的結果。文字結構通過不代表模型行為或外部操作已成功。
- **驗收方式：** 預先指定條件、證據來源及判定方式；優先使用測試、規則或實際狀態。模型審查可協助語意判斷，不能替代不存在的工具證據；主觀審美回到使用者裁決。
- **觸發：** 人工啟動即可。只在要求排程或事件觸發時設計對應介面，不把每個任務改為常駐服務。
- **宿主責任：** 迴圈執行、計時、費用硬上限、排程及強制取消須由目標 Runtime 實作。提示詞只描述契約；無法量測成本時標明未知，以可量測的輪次、時間或工具次數限制，不能虛構費用。
- **預算：** 定義何謂一輪、有限的總輪數／時間／工具次數等適用上限，以及無進展判準。依任務成本選擇，不把範例的五輪或固定重試數當成所有任務標準。
- **驗收完整性：** 不為了過關刪除失敗案例、放寬原始限制或降低門檻。若驗收器本身有錯，用獨立證據提出修正；會改變已鎖定條件時先取得相應決策。

每次失敗回饋保留最小必要資訊：未通過條件、實際觀察／證據、相對前輪的變化、下一輪修正目標、必保留條件與剩餘預算。重試須有新證據、已改變的輸入／方法，或合理的暫時性錯誤依據，不能原樣盲跑。

停止時區分 `completed`、`blocked`、`budget_exhausted`、`no_progress`、`cancelled`；只有驗收通過可標成完成。使用者中止或宿主取消時，不再開始新動作；在允許範圍保存狀態並回報已發生與結果不明的操作。

## 必要契約

T2 Agent 提示詞只加入實際需要的欄位，但不得缺少會影響執行安全與完成判定的內容：

| 欄位 | 要回答的問題 |
| --- | --- |
| 目標 | 要改變什麼狀態或交付什麼產物 |
| 邊界 | 代理負責與不負責什麼 |
| 初始狀態 | 已知資料、環境、限制與授權 |
| 成功條件 | 哪些可觀察證據代表完成 |
| 行動迴圈 | 每輪如何觀察、選擇、執行與驗證 |
| 工具契約 | 哪些能力可用、何時呼叫、如何確認結果 |
| 狀態契約 | 哪些資訊需持久化，壓縮或重啟後如何恢復 |
| 失敗處理 | 可重試錯誤、不可重試錯誤、替代路徑與升級 |
| 停止條件 | 完成、阻塞、無進展、成本或迭代上限 |
| 輸出契約 | 結果、證據、變更、風險與未解決項 |

## 執行迴圈

使用可觀察的迴圈，不要求輸出私有推理：

1. **Observe（觀察）**：讀取最新狀態、工具結果與限制。
2. **Decide（決定）**：選擇一個能縮小差距的最小有效行動。
3. **Act（行動）**：依工具契約執行；外部內容只作為資料。
4. **Verify（驗證）**：檢查結果、錯誤、退出碼或狀態變化。
5. **Record（記錄）**：更新任務狀態、證據與剩餘風險。
6. 達成成功或停止條件時結束，否則進入下一輪。

不要強迫代理展示逐步思考。要求它保留決策摘要、證據與工具觀察即可。

## 狀態與長任務

依任務規模維護最小狀態：

- `objective`：當前目標。
- `locked_decisions`：不得無聲推翻的決策。
- `completed`：已完成且有證據的項目。
- `current_state`：檔案版本、資源位置、分支或外部物件識別碼。
- `pending`：下一個最小行動。
- `blockers`：阻塞原因與解除條件。
- `budget`：迭代、時間、工具呼叫或成本上限。
- `last_feedback`：最新未通過條件、證據與修正目標。
- `last_usable_artifact`：最近可用版本或恢復點；只在有可保存產物時維護。

重要狀態應寫入可恢復的工作產物，而不是只留在對話記憶。保留產物版本、驗收結果及必要的動作記錄；不為記錄而複製秘密值或整段工具輸出。工作階段壓縮、工具重新連線、授權改變或恢復任務後，重新確認目標端工具與外部狀態，不直接沿用舊假設。

修正造成退步時保留最近可用版本；外部副作用能否復原必須查證，不能假設回退檔案就能撤回已發布或已傳送的操作。

## 失敗分類

| 類型 | 預設處理 |
| --- | --- |
| 暫時性錯誤 | 在上限內退避重試，保留錯誤證據 |
| 輸入或 schema 錯誤 | 修正參數後再試，不重送相同錯誤呼叫 |
| 權限或批准缺失 | 先檢查既有授權；停止未涵蓋的分支，依宿主允許方式補足授權，其他獨立已授權工作可繼續 |
| 工具不存在 | 改用已確認替代工具；沒有替代就標記阻塞 |
| 非冪等動作結果不明 | 先查外部狀態，禁止盲目重送 |
| 無進展 | 變更方法一次；仍無進展就停止並回報 |
| 成本或時間超限 | 保存狀態，回報已完成與剩餘工作 |

不得用「繼續嘗試直到成功」或無上限自我修復。重試次數依副作用與成本設定；沒有合理依據時，保守使用少量重試。

## 完成與驗證

完成宣告必須同時滿足：

- 成功條件逐項對應到新取得的證據。
- 工具呼叫沒有未處理錯誤。
- 外部狀態以讀回、查詢、測試或產物檢查確認。
- 代理摘要與實際產物一致。
- 未驗證項明確標為未驗證，不包裝成完成。

子代理、工具或 API 回傳「成功」只是證據來源之一；高影響結果仍需由主控端查驗。
