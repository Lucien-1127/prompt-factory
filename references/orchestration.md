# 多代理編排契約

> 只有任務涉及多代理、委員會、handoff、獨立 reviewer 或可安全平行的工作時讀取。

## 何時使用

只有至少符合一項才使用多代理：

- 工作可拆成彼此獨立、幾乎不共享可變狀態的分支。
- 需要不同專業或不同上下文，單一 Agent 會被無關資訊干擾。
- 需要實作者與獨立審查者分離。
- 長任務能以持久化產物交接，而非複製整段對話。

實際派遣仍須符合宿主提供的能力與授權；設計多代理提示詞本身不代表現在要派遣代理。

下列情況維持單一 Agent：

- 任務很小，協調成本高於工作本身。
- 多個分支會同時修改同一檔案、資料列或外部物件。
- 下一步依賴上一個結果，無法真正平行。
- 只是想靠「更多模型投票」掩蓋成功條件不清。

## 編排器責任

編排器只負責：

1. 拆分獨立工作單元。
2. 建立最小充分的 Task Packet（任務封包）。
3. 依可觀察條件路由。
4. 追蹤狀態、成本、依賴與衝突。
5. 驗證交付物並聚合結果。
6. 在重試上限後停止或升級。

不要在子代理完成後無理由重做全部工作。不要把需要同一可變狀態的工作同時派給多個寫入者。

## Task Packet

每個子代理只取得完成分支所需資訊：

```yaml
task_id: <stable-id>
objective: <single-responsibility-goal>
scope:
  include: [<allowed-targets>]
  exclude: [<forbidden-targets>]
inputs:
  artifacts: [<paths-or-ids>]
  facts: [<necessary-context>]
constraints: [<permissions-cost-time-style>]
dependencies: [<completed-task-ids>]
success_criteria: [<observable-checks>]
output_contract:
  status: DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED
  artifacts: [<paths-or-ids>]
  evidence: [<tests-observations-sources>]
  changes: [<what-changed>]
  concerns: [<risks-or-empty>]
```

優先交接檔案、識別碼、差異與結構化狀態，不把完整控制器對話塞給每個子代理。

## 平行與相依

只有以下條件全部成立才平行派遣：

- 輸入已足夠，不依賴另一分支尚未產生的結果。
- 寫入目標互斥，或所有分支都唯讀。
- 分支失敗不會使其他分支產生不可逆錯誤。
- 聚合規則已定義。

相依任務依 DAG（有向無環圖）順序執行。共享檔案的修改由單一擁有者整合；其他代理提供 patch、建議或審查結果。

## 審查模式

高風險或重要實作使用兩階段審查：

1. **Spec Review（規格審查）**：是否完整符合目標、範圍與成功條件。
2. **Quality Review（品質審查）**：正確性、安全、可維護性、測試與副作用。

審查者不得只根據實作者摘要下結論，應檢查實際產物與證據。修正優先交回原實作者，以保留上下文；同一問題超過設定上限仍未修復，再升級或更換。

## 衝突與聚合

- 事實衝突：以更直接、更新、可重現的證據優先。
- 建議衝突：依使用者成功條件、風險與成本排序。
- 寫入衝突：停止自動合併，交由單一整合者處理。
- 缺少證據：標記未驗證，不以多數票當成真實。
- 子代理失敗：保留成功分支，列出受影響的全域結論。

聚合輸出至少包含：整體結論、分支狀態、驗證證據、衝突裁決、未解決項與下一步。

## 停止與成本

- 每個分支設定重試或修正上限。
- 編排器另設整體預算與停止條件，避免每個分支都重設預算造成總成本膨脹；取消時停止新派遣並收集已完成或結果不明的動作。
- 同一錯誤重複出現時不得只重送相同提示。
- 達成本、時間或失敗分支門檻時保存狀態並停止。
- 授權判斷沿用[工具契約](tool-contract.md)：先檢查既有授權，只有新增權限、擴大範圍、關鍵條件改變或宿主要求時再確認；不因改成多代理而重複索取相同授權。
